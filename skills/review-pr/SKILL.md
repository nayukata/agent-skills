# PR レビュー支援

## 前提

このスキルはレビュアーの「コードリーディング」を支援するためのものである。
PRの変更を理解しやすく解説し、レビュアーが **判断** に集中できるようにする。

## 最優先原則: 易しい表現で簡潔に

認知負荷を最小化することが最重要。長文は読まれない。

- **1 指摘 = 本文 1〜4 行**（バッジ行を除く）。簡潔だと読み手が助かる。4 行を超えそうなら、装飾語を削る・例示を削る・複数文に分けず 1 文に圧縮する・別指摘に分けるのいずれかで収める。
- 専門用語は噛み砕く（「全置換セマンティクス」→「全部上書きする仕様」）。
- 英語の比喩・フレーズ (safety net / best practice / sanity check 等) は日本語に置き換える。コード識別子と確立された技術用語 (useMemo, reducer 等) はそのまま使ってよい。
- 装飾語・前置き（「〜について」「〜という観点で」）を削る。
- 同じことを言い換えて補強しない。1 回で伝える。
- 例示は本当に必要なときだけ。なくて伝わるなら入れない。

## 設計思想: Progressive Disclosure

ユーザーへの出力は段階的に開示する。一度に全情報を見せない。

- **L0 (初回)**: 結論 + 指摘テーブル（1 行要約）→ 全体把握
- **L1 (`N 番詳しく`)**: 個別指摘の背景・提案を展開 → 妥当性判断
- **L2 (`全部詳しく`)**: 全指摘の本文を展開 → 通読
- **L3 (`レビューコメントを投稿`)**: 実際の PR への副作用 → 不可逆な操作の前にプレビュー

副次的に効いている原則:
- Hick の法則: アクション選択肢を 3 つに絞る
- Doherty Threshold: 即判断できる情報粒度に圧縮

## 実行手順

### 1. PR情報の取得

ユーザーから受け取った PR URL から owner / repo / PR 番号を抽出し、以下の情報を取得する。

```bash
# PR の基本情報
gh pr view $PR_NUMBER --json title,body,author,baseRefName,headRefName,files,additions,deletions,commits

# 差分の取得
gh pr diff $PR_NUMBER

# PR コメント（インラインコメント含む）
gh api repos/{owner}/{repo}/pulls/{pr_number}/comments
gh pr view $PR_NUMBER --json comments,reviews
```

### 2. 変更の全体像を解説

以下の構造で、レビュアーが「何をどう読めばいいか」のガイドを提供する。

```
## 変更の全体像

### この PR は何をしているか
[PR の目的を1-3文で。説明文の要約ではなく、差分を読んだ上での理解]

### 変更の構造
[ファイル群を意味的なまとまりでグループ化して説明]
- グループA: [目的] — `file1.ts`, `file2.ts`
- グループB: [目的] — `file3.ts`

### 読む順序の提案
[依存関係や理解の流れを踏まえた、推奨する読み順]
```

### 3. 注目すべきポイントの提示

差分を精読し、以下を報告する。

#### 設計判断の評価

- 選択されたアプローチは妥当か
- 見落とされている代替案はないか
- CLAUDE.md やrulesの設計原則との整合性

#### 潜在的な問題

問題がある場合のみ、以下のラベル（shields.io バッジ）で報告する。会話内サマリでは badge の代わりに英大文字プレフィックス（`MUST:` / `IMO:` 等）でも可だが、**インラインコメント投稿時は必ず badge を使う**。

| バッジ | 色 | 用途 |
|---|---|---|
| `![must-badge](https://img.shields.io/badge/review-must-red.svg)` | red | マージ前に対処が必要 |
| `![should-badge](https://img.shields.io/badge/review-should-teal.svg)` | teal | 強く推奨する改善 |
| `![imo-badge](https://img.shields.io/badge/review-imo-orange.svg)` | orange | 個人意見・議論余地あり |
| `![ask-badge](https://img.shields.io/badge/review-ask-yellowgreen.svg)` | yellowgreen | 意図確認・質問 |
| `![nits-badge](https://img.shields.io/badge/review-nits-green.svg)` | green | 細かい指摘 |
| `![good-badge](https://img.shields.io/badge/review-good-blightgreen.svg)` | blightgreen ※ユーザー定義の表記 | 良い判断への称賛 |
| `![next-badge](https://img.shields.io/badge/review-next-blueviolet)` | blueviolet | 後続タスク・別 PR で対応 |

**迷ったら一段下げる**: must は契約破壊 / 障害級のみ。それ以外は should 以下に振る。

### 4. メンタルモデル不在の検出

以下の兆候がある箇所を特定し、**柔らかい質問文**として提示する。

以下の兆候を確認する

- 動くが理由が説明できないコード
- 過剰に防御的なエラーハンドリング（何が起きるかわからないから全部 catch）
- コピー元が不明な定型コード
- テストはあるが、テスト対象の振る舞いの「なぜ」が説明できない
- 不自然に冗長な実装（シンプルな代替案が存在するのに選ばれていない）
- PR説明文が「何を変えたか」しか書いておらず「なぜ」がない
- インラインコメントがなく、複雑なロジックの意図が不明

**質問文のトーン**

詰問ではなく、理解のための対話を促す柔らかい質問にする。

良い例:
- 「この部分で `RetryPolicy` を3回に設定されていますが、この回数はどのような基準で決められましたか?」
- 「`handleError` 内で全例外を catch されていますが、特定の例外のみ処理する設計も考えられそうです。意図的に広く取られている理由があれば教えていただけますか?」
- 「こちらのロジックは〇〇と似た構造に見えますが、共通化せず個別に実装された背景がありましたら共有いただけると助かります」

悪い例:
- 「なぜこうしたんですか?」（漠然すぎる）
- 「これは間違っています」（判断の押しつけ）
- 「理解していますか?」（人格への攻撃）

### 4.5 既存指摘の扱い

PR に既に残されているコメントには、原則として同調コメントを残さない。
同調は PR のシグナルを薄めるだけで、PR 作成者の作業を増やす。

- リアクションで済むならリアクションで
- HEAD で問題が残っており、かつ既存指摘と異なる角度で書くべき内容がある場合のみ
  独立した自分の指摘として投稿する
- その際は `gh api "repos/{owner}/{repo}/contents/{path}?ref={HEAD_SHA}"` で
  HEAD のファイル内容を確認し、指摘が現在も該当するかを検証する

### 5. 初回出力（結論ファースト）

スキル起動直後の最初の応答は、以下の構造で簡潔に出力する。
詳細展開やインラインコメント投稿は、ユーザーからの追加指示を待つ。

```markdown
## レビュー結果
- **規模**: [S/M/L] (+追加/-削除, ファイル数)
- **総評**: [1 行で要件カバレッジ / 設計妥当性を要約]
- **リスク**: [破壊的変更 / セキュリティ / なし]
- **指摘**: [バッジ別件数 例: SHOULD 2 / ASK 3 / IMO 1]

## 要件カバレッジ（外部チケットがある場合のみ）

| サブタスク / 受け入れ条件 | 対応する変更 | 充足 |
|---|---|---|
| ... | ... | OK / 部分 / 不足 |

## 指摘一覧

| # | バッジ | ファイル:行 | 要点 |
|---|---|---|---|
| 1 | SHOULD | file.ts:42 | [事実] → [提案 / 確認] |

**次のアクション**: 以下のいずれかを指示してください
- `N 番詳しく` … 指定した指摘の背景・提案を展開
- `全部詳しく` … 全指摘を展開
- `レビューコメントを投稿` … PR にインラインコメントとして投稿（投稿前にプレビューします）
```

#### 要点列の書き方

「事実 + 矢印 + 提案 / 確認」の 1 文構造にする。
セル内改行はしない。テーブルだけで指摘の妥当性を判断できる粒度を目指す。

例: `role に @maxLength 制約なし → 他項目同様に DB スキーマ上限で付与`

「良い点」セクションは出さない（指摘の不在 = 良い判断）。

### 6. インラインコメント投稿（ユーザー指示があれば実行）

ユーザーが「インラインで投稿して」「PR にコメント残して」等と指示した場合のみ実行する。投稿前に必ず内容を提示し、**承認を取ってから** `gh api` で投稿する。

#### プレビュー表示の必須要件

「プレビュー」と称して `file:line + 1 行要約` のリストだけを出すのは NG。ユーザーは GitHub に出る最終的な日本語表現を見て承認するため、**実際に投稿される本文をそのまま見せる**こと。

必須項目:
1. **PR 本体メッセージ** の全文（バッジ列挙ではなく、実投稿予定の文章）
2. 各インラインコメントごとに以下をブロック分けして全文表示
   - 何番目の指摘か（番号）
   - `path:line` と バッジ種別
   - 本文の全文（バッジ画像行を含め、投稿される改行構造のまま）
3. 提示後に「この内容で投稿してよろしいですか？」と確認を取る

提示フォーマット例（指摘 1 件分）:

```markdown
**① `apps/server/src/foo.ts:42` (SHOULD)**

> ![should-badge](https://img.shields.io/badge/review-should-teal.svg)
>
> 本文 1 文目。
> 本文 2 文目。
> 本文 3 文目！
```

NG なプレビュー（要約だけ・本文が見えない）:

```markdown
- `foo.ts:42` (SHOULD) — XXX が YYY → ZZZ
- `bar.ts:10` (ASK) — AAA の意図確認
```

#### 投稿フォーマット規約

**1 行目はバッジ画像** にする（プレフィックス文字列は使わない）。本文（バッジ行を除く）は **1〜4 行** に収める。

```
![ask-badge](https://img.shields.io/badge/review-ask-yellowgreen.svg)
本文 1 文目。
本文 2 文目。
本文 3 文目。
```

長くなりそうな時の縮め方:
- 「〜という観点で」「〜について」「〜のような」など装飾を削る
- 1 文で言えるなら 1 文にする（背景 + 指摘を 1 文に圧縮）
- 別観点が混ざっているなら指摘を分割する

#### 文体ガイドライン

- **改行**: 文ごとに改行する（`\r\n` で区切る）。1 段落に詰め込まない。
- **疑問符**: 全角 `？` を使う（半角 `?` は使わない）。
- **温度感**:
  - 文末の選択は本文の温度感と一体で考える
  - `！` は本文全体で最後の文末 1 個まで（連発禁止）。中間文は句点 (`。`) で締める
  - レビュー全体で `！` を含むコメントは半数以下を目安（全部に付けると機械的に感じる）
  - 「。」止めが自然なケース: 推測・提案・共感の語尾（「〜かなと思います」「〜はどうでしょう」）
  - 「！」付きが自然なケース: 提案・呼びかけ・推奨（「〜検討してみてください！」「〜と思います！」）
  - 「。」止めで威圧的になる典型: 断定形（「〜すべきです。」「〜になります。」「〜です。」）が連続する文
    → 本文の語尾を柔らかい形に書き直すか、`！` を残す
- **語尾の重複回避**: 1 コメント内で同じ語尾を 2 回以上繰り返さない。特に「〜そうです」は AI 的な癖として目立つので 1 回までに絞る。コメントを書き終えたら全文検索で重複チェックする。
  - パターン: 「A できそうです。B になりそうです！」のように「〜そうです」が連続する形
  - 改善: 1 文目を「〜と思います」「〜できます」「〜かもしれません」「〜になりかねません」などに置き換える
  - 同様に「〜になります」「〜なる」「〜です」も 3 連発で出てきたら言い換える
- **「〜してしまう」はネガティブ含意専用**: 「してしまう」は望ましくない結末に対して使う表現（「壊してしまう」「捨ててしまう」）。提案や推奨アクションでポジティブな結末を導く文脈には使わない。
  - パターン: 「[望ましい変更] してしまうと [良い結果] になります」のように「してしまう」+ 好ましい結末
  - 改善: 「してしまう」を取り除いて「[望ましい変更] にすると [良い結果] になります」にする
  - 「〜にしてしまう」「〜してしまった方が」「〜倒してしまう」が出てきたら「〜にする」「〜した方が」「〜倒す」に直す
- **語尾の柔軟化**:
  - 「消せます」→「避けられます」（強い断定を避ける）
  - 「不明でした」→「分かりませんでした」
  - 「（こちらで対応）」→「しますね」（業務的な括弧書きを避ける）
  - 「安心です」→「安心だと思います」（断定より推測形の方が自然）
  - 「〜になります」→「〜になっています」「〜です」（断定が連続するときに語尾を変える）
- **事実と推測を区別**: 差分を見れば分かる事実に推測形を使わない。
  - 良い: 「テストが見当たりませんでした」「型注釈が省略されています」
  - 悪い: 「テストがなさそうです」「型注釈が省略されているようです」
  - 本当に推測のときだけ推測形 (例: 「意図的かもしれません」)
- **3 要素構造**: 事実だけを断定で並べると機械的に響く。「主観 (気になりました等) + 事実 + 提案」を意識すると温度感が出る
- **括弧内の具体例を入れない**: `（例: \`code\` は「...」?）` のような挿入はしない。例示が必要なら別の文として独立させる。

#### 行番号の取得

ローカルブランチが PR のブランチと異なる場合、ローカルの `grep` 結果は古いコードを参照する。
インラインコメント投稿時は、必ず PR の HEAD commit からファイル内容を取る。

```bash
# HEAD SHA を取得
HEAD_SHA=$(gh pr view $PR_NUMBER --json headRefOid -q .headRefOid)

# HEAD でのファイル内容から行番号を取得（path に ? を含むのでクォート必須）
gh api "repos/{owner}/{repo}/contents/{path}?ref=$HEAD_SHA" -q .content \
  | base64 -d | grep -n "<target string>"
```

zsh では URL の `?` がグロブ展開されるため、`gh api` の引数は必ずダブルクォートで囲む。

#### 投稿時の body の書き方

PR の body は 2-3 文の人間的なメッセージに絞り、**必ずアクションの呼びかけを含める**。
会話画面用のテーブル・規模・件数の構造化サマリは入れない。

構造:
1. 全体評価 (1 文)
2. 残した指摘とお願い (1-2 文 — ご確認 / ご対応 / コメント等のアクションを明示)

**件数の列挙はしない**: 「SHOULD を N つ、ASK を M つ残しています」のようなバッジ別カウントは AI が書いた感が強く出る。代わりに「何について」残したかの中身（変更領域・テーマ）を一言で添える。

- パターン: 「[バッジ名] を N 個、[バッジ名] を M 個残しています」
- 改善: 「[変更領域 / テーマ] について気になる点を残しました」のように内容で表現する
- 領域の言い換え例: 「エラー処理まわり」「命名と責務の境界」「テストカバレッジ」「型の取り回し」など、PR の指摘群を一言で括れる名詞句にする

#### 投稿コマンド

```bash
# JSON ペイロードを作成
cat > /tmp/pr-review.json <<'EOF'
{
  "commit_id": "<head SHA>",
  "body": "<2-3 文の人間的な要約 — テーブル禁止>",
  "event": "COMMENT",
  "comments": [
    {
      "path": "<file path>",
      "line": <line number>,
      "body": "![ask-badge](...)\n本文..."
    }
  ]
}
EOF

gh api -X POST repos/{owner}/{repo}/pulls/{pr_number}/reviews --input /tmp/pr-review.json
```

`event` は原則 `COMMENT`（承認 / 変更要求は明示的な指示があったときのみ `APPROVE` / `REQUEST_CHANGES`）。

## 注意事項

- PR作成者への敬意を忘れない。批判ではなく理解のための分析
- 作成者の説明文やコメントがある場合は、それを尊重した上で差分と照合する
- 自動化で検出可能な問題（lint違反、型エラー）にはあえて言及しない
- 「問題なし」も価値ある結論。無理に指摘を絞り出さない

# Writing Tasks

タスク管理ツールへのチケット起票時の記述方針。ツール非依存。

## 前提

チケットとPRは役割が違う。チケットに実装の詳細を記述しないこと。

| 場所 | 書く内容 | 読み手 |
|---|---|---|
| チケット | 「何が起きているか」「何が必要か」 | 関係者全員(非エンジニア含む) |
| PR/コミット | 「どう直したか」「どう実装したか」 | レビュアー |

## 基本原則

### 1. ユーザー視点で書く

- 不具合: 「ユーザーから見て何が起きているか」
- 機能要求: 「ユーザーが何をしたいか」
- 実装詳細(関数名/ファイル名/ライブラリ名/言語仕様)は書かない

### 2. 構造化された自然言語

- 見出し / 箇条書きで構造化(項目が複数ある場合)
- 散文として自然に読める日本語
- 1項目あたり1〜3行で簡潔に

### 3. 「対応」「原因の分析」を本文に書かない

それはPR/コミットメッセージの責務。チケットには現象/要件だけ。

### 4. 目的・背景・判断理由を残す

機能追加 / 変更要求 / 方針転換のチケットでは「なぜそうするのか」を本文に残す。

- 数ヶ月後にチケットを見返したとき、「何を決めたか」だけでなく「なぜそう決めたか」を追えるようにする
- 「Aを採用してBを採用しなかった」など検討した選択肢がある場合、不採用理由も書くと判断の追跡可能性が上がる
- ここで書くのは **この変更が必要な理由(WHY)** 。**実装方針の理由(HOW)** はPR/コミットの責務で、混同しない
- 背景や目的が明確でない場合、AskUserQuestionツールでユーザーに確認する

## 禁止事項

| 禁止 | 理由 |
|---|---|
| 関数名 / クラス名 / メソッド名 | 読み手は実装を知らない |
| ファイルパス / ディレクトリ名 | 同上 |
| ライブラリ名 / フレームワーク名 / 言語仕様 | 同上 |
| スタックトレース / エラーコード抜粋 | ユーザー視点の現象に翻訳して書く |
| `AS-IS / TO-BE` 構造 | チケットは要件、PRは対応 |
| 「原因」「対応」セクションの併記 | PRに任せる |
| `fix(scope):` `feat:` 等のコミットprefix | チケットはコミットではない |
| 「動作確認」「テスト結果」セクション | PRに書く |

## ユーザー語彙への翻訳表

| ❌ 技術用語 | ✅ ユーザー語彙 |
|---|---|
| TypeError が発生 | サーバーエラーが発生 |
| 500レスポンス | エラー画面が出る / 操作が失敗する |
| 自動リンク化regexが認識しない | リンクとして表示されない |
| Null チェック漏れ | 特定のケースで動作しない |
| クエリ未エンコード | 一部の文字が原因で動かない |

## テンプレート

### 不具合報告(複数項目)

```
### 1. [現象を1文で]

[何をしようとすると / 何が起きて / ユーザーが何に困るか。1〜3行]

### 2. [現象を1文で]

[同上]
```

### 機能追加 / 変更要求

```
### 概要

[誰が / 何を / どうしたいか]

### 背景 / 目的

[なぜこの変更が必要か。検討した選択肢と採用/不採用の理由があれば明記]

### やりたいこと

[要望をユーザー視点で。実装方針 / 技術選定は書かない]
```

## Example: 不具合チケット

### ❌ Before(技術的すぎる、PRっぽい)

```
## 不具合
ログイン/決済まわりで2件のバグ。

### 1. ログインAPIで NullPointerException
- `userRepository.findByEmail()` が None を返したときに `.is_active` 参照で NPE
- 本番のSentryで観測済み
- 対応: Optional チェックを追加して None ガード

### 2. 決済画面で金額計算が壊れる
- カート内の数量が空文字列のときに `parseInt` が NaN を返し合計金額が NaN になる
- 対応: 数量が空のときは 0 として扱うようバリデーション追加
```

問題点:
- 関数名 / 型名 / ライブラリ概念がチケットに混入
- 「対応」を本文に書いている(PRに任せる範疇)
- ユーザーから見えない概念(NaN, NPE, Optional)が出ている

### ✅ After(ユーザー視点、現象のみ)

```
### 1. 一部のユーザーがログインできない

特定のメールアドレスでログインしようとするとエラー画面が表示され、ログインに失敗する。

### 2. 決済画面で合計金額が正しく表示されないケースがある

カート内の商品数量を空欄のまま決済画面に進むと、合計金額の表示がおかしくなり、注文を確定できない。
```

## Example: 機能追加チケット(背景・判断理由を含む)

### ❌ Before(背景なし、何をするかだけ)

```
### 概要
ログイン画面に「Googleでログイン」ボタンを追加する。

### やりたいこと
SSOボタンを実装する。
```

問題点: 数ヶ月後に見返したとき「なぜGoogleなのか」「なぜSSOなのか」「なぜ今やったのか」がわからない。

### ✅ After(背景・判断理由あり)

```
### 概要
ログイン画面に「Googleでログイン」ボタンを追加する。

### 背景 / 目的
新規ユーザー登録の離脱率がパスワード入力ステップで30%と高い(2026-04のアナリティクス)。SSO導入で離脱を減らしたい。
SSO候補は Google / Apple / Microsoft があったが、ターゲット層の Google アカウント保有率が95%と最も高いため Google を優先採用。Apple は次フェーズで検討する。

### やりたいこと
ログイン画面に「Googleでログイン」のボタンを表示し、Google アカウントでサインアップ・ログインできるようにする。
```

## 関連リンクの記法

PR / 親チケット等のリンクは本文の末尾にシンプルに添える。

```
PR: https://github.com/.../pull/123
親チケット: https://app.clickup.com/.../xxx
```

「動作確認済み」「テスト pass」等は書かない。動作確認はPRの責務。

## チェックリスト(起票前)

- [ ] 複雑な専門用語を多用せず、わかりやすい自然言語で書かれているか
- [ ] 日本語と英語が入り混じっていないか
- [ ] 「対応」「原因」を本文に書いていないか
- [ ] 1項目あたり3行以内に収まっているか
- [ ] 見出しは現象/要件を表す自然な見出しになっているか
- [ ] 関連リンクは末尾に分けて配置したか
- [ ] 機能追加/変更要求の場合、なぜそうするのか(背景/判断理由)が書かれているか

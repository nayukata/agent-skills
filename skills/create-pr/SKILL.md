# PR を作成する

## 併用する文章規範

PRタイトル、PR本文、インラインコメントを書く前に、`../japanese-tech-writing/SKILL.md`を全文読む。
論証のつながり、読み手の負荷、冗長性、事実と推測の区別に適用する。

プロジェクトのPRテンプレート、GitHub記法、必須出力形式は、このskillの指定を優先する。
文章の温度感や語尾についても、このskillの文体ルールを優先する。

## 前提

コードレビューの本質は「バグ発見」ではなく「これは自分たちのプロダクトに組み込むべきか」というチームの判断行為である。
PR作成者の責務は、レビュアーがその判断を下せるだけの文脈を提供すること。
大量の情報で圧倒するのではなく、コードリーディングの助けとなる説明文を書く。

## 目的

- レビュアーの認知負荷を最小化する
- 実装や変更の意図を正しく伝える
- 不明点は推測で記述せず、ユーザーの意図を確認する

## 長さの予算

本文は足すほど読まれなくなる。以下を目安にし、超える分は `<details>` に畳むか、書かない。

| 対象 | 目安 |
|---|---|
| 概要 | 3 文以内 |
| 見出し (`##` と `###` の合計) | 6 個以内 |
| 本文全体 | 地の文と箇条書きで 1,200 字以内 (図・表・画像・折りたたみの中身は数えない) |
| 段落 1 つ | 3 文以内、120 字程度。原因の説明でも 2 段落まで |
| 箇条書き 1 項目 | 1 文。長くても 2 文、80 字程度 |

行数ではなく文字数で数える。段落は改行せずに書くため、行数は長さの指標にならない。`wc -m` で測る。

変更内容の 1 件に書く中身は「これまでどうだったか」「こう変えた」「何が変わって見えるか」の 3 つである。これは中身の一覧であり、文の並びの型ではない。段落は、その変更の主役 (原因、判断、結果のどれか) から書き始め、文の数と長さは内容に合わせる。1 節だけの短い文も使う。どの段落も同じ書き出しと同じ文数になっていたら、型に当てはめて書いている。4 文目が要るなら、それは原因の解説か設計判断であり、図・表・折りたたみのどれかに移す。

追加の節を使うときは、変更内容側の見出しを減らして合計 6 個に収める。箇条書きの 1 項目が 2 文を超えたら、それは段落である。箇条書きの記号を外して地の文で書く。

「変更していないもの」の列挙は書かない。レビュアーが心配しそうな 1 点に限り、その変更の段落の直後に「確認したい点：」で始まる 1 行で書く。

## 文体ルール

### 英字の使い方

地の文はカタカナ・ひらがな・漢字で書く。英字を書いてよいのは、製品・技術の正式名称、日本語に定着した略語、バッククォートで囲んだコード識別子のみ。

迷ったら以下の順で判断する。

1. その英単語はコードやAPIの識別子・概念名を指しているか？ YES ならバッククォートで囲む。
2. 普段のチャットや会話で自然に口から出るカタカナ語か？ YES ならカタカナ化。
3. どちらでもなければ日本語で書く。

英字の動詞（`unskip` / `propagate` / `resolve` 等）とカタカナで意味が通らない英単語（`wire format` / `composition` 等）は必ず日本語化する。

このルールは「識別子を残す線引き」を上書きしない。エンドポイントのパス、コマンド、環境変数名は、英字であってもバッククォート付きでそのまま書く。

### 時制

PR本文の動作記述は完了形で書く。「〜します」を裸で使わない。

| 何を書く | 時制 |
|---|---|
| 本PRに含まれる変更 | 完了形（〜しました） |
| 意図・目的 | 名詞化（〜が目的です） |
| 変更前の状態 | 過去形（〜されていました） |
| 過去の観測・報告 | 過去形（〜発見しました） |
| 変更後の体験 | 現在形（〜できます／〜されます） |
| 本当の未来 | 時系列マーカー付き（これから〜・別PRで〜・〜予定です） |

### 敬語と語尾

- 自然な敬語（〜です／ます／しました／お願いします／思います）
- 同じ語尾を連続させない
- 「〜してしまう」は望ましくない結末専用。望ましい変更を説明する文脈では「〜にする」と書く

### 事実と推測

差分から分かる事実に推測形を使わない。本当に推測のときだけ推測形にする。

### 言い訳がましい言い回しを避ける

「〜位置づけです」「〜見当たりませんでした」「〜する余地があります」「〜になりうります」といった間接表現は使わない。事実は完了形で断言、必要性がなければ書かない。

将来リスクの回避提案は前提が実在するか確認してから書く。前提が実在しないなら書かない。

### 業界用語の名前は本文に残さない

平文で説明できる技術用語は、平文で書き切る。用語名を括弧書きで添える必要はない。用語自体が話題（用語比較、用語選定の議論）の時だけ用語名を書く。

### 言い換えで抽象度を上げない

日本語化は、置き換え先が元の語と同じ範囲を指すときだけ行う。置き換えた結果、意味の範囲が広がる、または別分野の語として読めるなら、その言い換えは使わない。定着したカタカナ語で書くか、対象の具体物をバッククォート付きで書く。

判断は2点。置き換え先だけを読んで元が何だったか復元できるか。法務・契約・組織など別分野の話と誤読されないか。どちらかが落ちたら不可。

滑らせやすい置き換え：API 仕様を「契約」、エンドポイントを「窓口」「入り口」、ユーザー ID を「識別子」「目印」、リクエスト本文を「中身」、キューを「待ち行列」、コールバックを「呼び戻し」、トークンを「合言葉」「鍵」。

### 括弧書きの補足は最小限

括弧書きは視線を切って戻す動作を強いる。重要な情報なら普通に書き、要らないなら消す。

## PR構造

### 標準の3節

デフォルトは以下の3節のみで書く。

    ## 概要
    [この PR で何が変わるかを 1-3 文で。ユーザー/システム視点で]

    [PR 全体に関わる Alert があれば、ここに 1 つだけ。マージ順・対の PR の前提・破壊的変更]

    ## 変更内容
    [主要な変更 2〜3 件。1 件 1 段落で、これまで／こう変えた／何が変わって見えるか を書く。書き出しと文の数は、段落ごとに内容で決める]
    [判断を仰ぐ点は、その変更の段落の直後に「確認したい点：」で始まる 1 行。その変更だけに関わる Alert も、この段落の直後]

    ## 動作確認
    [結果を 1 行。再現に前提が要るときだけ前提を添える。テストの内訳は折りたたむ]

読む順は上から、概要 → 変更内容 → 動作確認で固定する。判断を仰ぐ点は、それに要る文脈を読んだ直後に置く。概要の直後に並べると、レビュアーは何の話か分からないまま判断を求められ、末尾の節に置くと、そこまでスクロールした人しか読まない。

### 追加できる節（該当時のみ、空なら書かない）

| 節 | 書くのは... |
|---|---|
| `## 設計の意図` | 差分だけでは判断ポイントが読み取れない設計判断がある時 |
| `## トレードオフ` | 検討した代替案を捨てた理由を残したい時 |
| `## 影響範囲` | 変更が他コンポーネント/機能に波及する時 |
| `## 関連リンク` | 対のPR・仕様書がある時 |

- 空節は削除する。「なし」「TBD」と書かない
- 関連PRは概要末尾に1行で書ける場合はインライン化

### AS-IS/TO-BE 節を独立に書かない

「変更前／変更後」を独立節に切り出さない。状況変化を書く時は、変更内容の各見出しの段落の中で、変更前の状況から変更後までを続けて書く。純リファクタでは省略。

### 絵文字テンプレは廃止

判で押した絵文字見出しと「変更の種類」チェックボックス群は情報の粒度差を潰す。テンプレに従わず、内容に応じて必要な節だけ残す。

## 変更内容の書き方

### ユーザー観点で振る舞いを書く

本文には振る舞い（何が起きるか）と設計判断（なぜそうしたか）だけ書く。実装の場所（ファイルパス・関数名・変数名・クラス名）は書かない。差分で見えるため。

主語はコンポーネント名やファイル名でなく、「ユーザーの体験」や「機能の仕様」にする。

### DB内部語彙で抽象化しない

「保存先」「テーブル」「レコード」「行」は差分の読者にも遠回り。ユーザーから見える現象で書く。

### 判断の観点は触れた場合だけ 1 行

異常系（エラー・空データ・境界値）、認証境界、既存機能への影響は、差分がそこに触れている場合に限り 1 行で書く。触れていないなら書かない。網羅しようとすると本文が観点の一覧になり、主題が埋もれる。

### 識別子を残す線引き

以下のケースは識別子を書いてよい。

- 中心概念で本文中に繰り返し参照される（PRの主題そのもの）
- 削除対象の名指し
- 範囲の説明として不可欠
- 議論の対象そのもの（命名レビュー、除外リスト等）
- 場所の特定手段（エンドポイントURL、コマンド）
- 外部要因の根拠（使用ライブラリ名、API仕様名）
- デプロイ手順・利用者が設定する対象（実行コマンド、環境変数）

コマンド識別子（`make format` 等）はバッククォート付きで本文に残してよい。

### 概念（`識別子`）の初出補足形

初出で内部用語を出すときは、概念を普通の言葉で書き、識別子を（`code`）で添える。太字は段落の結論に使うため、ここでは使わない。

### 反復禁止

同じ情報を概要／変更内容／確認したい点／動作確認で書き重ねない。1度だけ、一番読ませたい場所に置く。

セキュリティ・認可話は特に反復されがち。書き終えたら「認可の話を何回書いたか」を数える。

### バグ修正／リファクタでも挙動変化は独立見出しで明示

- リファクタでもユーザー可視の変化があれば独立見出しで切り出す
- 「バグ修正」ラベルだけでは足りない場合、挙動変化節を切り出す
- 純リファクタは「挙動不変」を最初に明言し、AS-IS/TO-BE を書かない

### 「刷新」「修正」の区別

- 新規実装を「修正」「刷新」と書かない
- 既存の挙動を変えるのが「修正」
- 新しい機能を追加するのが「新規」
- 環境整備は「対応」

## 折りたたみ `<details>`

`<details>` は本流には不要だが深掘りしたい人には残しておきたい情報に使う。レビュアーに判断してほしい情報は折りたたまず本文に置く。

- 使う：長大なテストログ、失敗した代替案の詳細、テンプレの義務項目/チーム慣習で書きたい「変更ファイル一覧」等の機械的な列挙
- 使わない：確認したい点で名指しした対象、動作確認の結論、設計判断の中核、レビュアーに判断してほしい設定値

## GitHub の視覚補助

本文を書き終えたら、そのまま提出せず「縦に長い文章の塊になっていないか」を点検する。以下の3つは装飾ではなく、レビュアーが読む順番と滞在時間を設計する手段である。

### GitHub Alerts

`> [!NOTE]` `> [!TIP]` `> [!IMPORTANT]` `> [!WARNING]` `> [!CAUTION]` の 5 種。

使うのは、知らずに進めると判断や手順を誤ることに限る。破壊的変更、移行手順、マージ順や対の PR の前提、既存データへの影響がこれにあたる。PR 全体で 2 つまで。

置く場所は、その内容が関わる場所に合わせる。

| 関わる範囲 | 置く場所 |
|---|---|
| PR 全体（マージ順、対の PR の前提、破壊的変更） | 概要の直後に 1 つまで |
| 特定の変更の副作用（既存データや出力の変化） | その変更の段落の直後 |
| 確認や反映の手順（移行の順序、必要な設定） | 動作確認の節 |

判断を仰ぐ点は Alert にしない。その変更の段落の直後に「確認したい点：」で始まる 1 行で書く。段落を読んだ直後なら、レビュアーは文脈を持ったまま判断できる。本筋から外れる補足は `<details>` か 1 文の箇条書きに置く。

種類は温度で選ぶ。対応が必須なら `IMPORTANT`、放置すると壊れるなら `WARNING`、知っておけばよいだけなら `NOTE`。

### Mermaid 図表

以下に該当する変更で強く推奨。

- 状態遷移の変更 → `stateDiagram-v2`
- コンポーネント・モジュール間の依存関係変更 → `graph LR` / `flowchart`
- API 呼び出し順序・複数システム連携 → `sequenceDiagram`
- DB スキーマ変更 → `erDiagram`

複数の登場人物が絡む処理の流れは、`flow-diagram` スキルの HTML の図にして、PNG で貼る。同じ入力が複数の経路に分かれる、不具合の発生経路が3ステップ以上ある、変更前後で結末が分かれる、2つの処理が同時に進む、がこれにあたる。登場人物ごとに動く場所を分けて示せるので、「なぜ食い違ったのか」を文章で追わせずに済む。原因の説明が2段落を超えたら、図に置き換えられないか検討する。単純な状態遷移・依存関係・呼び出し順序は Mermaid のままでよい。

図には具体的な数値を入れる。「時間が足りない」より「残り8分に15分」のほうが、図だけで理解が完結する。

### 表

以下は表にする。文章で書くと読者が値を記憶しながら読む必要が生じる。

- 2つ以上の条件で値が異なる（初診と再診、変更前と変更後など）
- 数値の対比や増減
- テストや確認項目と、その結果の対応

比較の軸は列に、比較対象は行に置く。強調したいセルは太字にする。

### 太字

レビュアーが持ち帰る結論がある段落では、その結論を 1 か所だけ太字にする。変更後に何が起きるか、判断を求める選択肢、数値の結論がそれにあたる。結論と呼べるものが無い段落は、太字なしでよい。太字にするのは文全体ではなく結論の語句だけで、太字の部分だけを拾い読みして結論が分かる語句を選ぶ。句点は太字の外に置く。「確認したい点」のラベルは、この 1 か所とは別に `**確認したい点**：` の形で太字にする。太字の記号 `**` の内側の先頭と末尾には、句読点・コロン・かぎ括弧・丸括弧を置かない。GitHub は記号に接した `**` を太字の区切りと認識せず、記号のまま表示する。1 段落の太字は、結論の 1 か所と「確認したい点」のラベルを合わせて 2 か所までにする。それより多いと、どれが結論か分からなくなる。

### 見出しの数を抑える

主要な変更 2〜3 件だけ見出しを立てる。残りの小さな変更は `<details>` に畳むか、1 文の箇条書きにする。

    - **枠がちょうど収まる場合の扱いを揃えました。** 従来は境界で拒否していました。

太字リードの後ろに説明を連ねて 1 項目が数百字になった箇条書きは、見出しを減らした意味が無い。説明が要るなら見出しを立てて段落で書く。

## 実行手順

### 1. 差分の把握

- `git log` と `git diff` で変更の全体像を把握する
- 変更ファイル数が多い場合は、意味的なまとまりでグループ化して理解する

### 2. インラインコメントの計画（必須出力）

PR本文を作成する前に、以下の条件に該当する箇所を探し、必ず「インラインコメント案」としてテキストに書き出す（出力する）。

- 差分だけでは意図が読み取りづらい複雑なロジック
- 一見不自然に見えるが理由がある実装（ワークアラウンド、制約回避など）
- レビュアーが「なぜこうしたのか」と疑問に思いそうな判断ポイント
- なるべく1、2行に収める
- その差分だけを読む人に伝わる自己完結した内容にする
- コード側に既にコメント（`# ...` / `// ...`）が付いている箇所には重ねない。二重コメントになる

該当箇所がない場合でも「インラインコメント対象：なし」と出力する。

出力フォーマット：

- 対象ファイル
- 対象コードの概要と行数の目安
- コメント内容

### 3. PR テンプレートの確認

    ls .github/pull_request_template.md .github/PULL_REQUEST_TEMPLATE.md .github/PULL_REQUEST_TEMPLATE/ pull_request_template.md 2>/dev/null

テンプレートが存在する場合、絵文字見出し・「変更の種類」チェックボックス・空節は本PRで採用しない（削除して提出）。チーム慣習で「変更ファイル一覧」等のテーブルを書きたい場合は `<details>` に畳んで本流の可読性を保つ。

テンプレートが存在しない場合、標準の3節（概要／変更内容／動作確認）を使う。

### 4. 動作確認の再現に要る前提を明記する

再現に前提が要る確認には、その前提を添える。前提が無いなら書かない。再現の前提は動作確認の節に書く。マージ順や対の PR の前提だけが、概要直後の Alert の対象になる。

- 対のPR・別リポ・別ブランチを同時に動かす必要があるか
- 特定の環境変数・フィーチャーフラグ・seed データが必要か
- 起動が必要なサービス、または接続先
- マイグレーションやデプロイの順序指定

複数のリポ/PRが揃って初めて動く変更は、片方の PR しか見ないレビュアーが必ずいる前提で、関係する各 PR に前提を書く。

### 5. 本文の点検

本文を書き終えたら、`gh pr create` を実行する前に、次の順で点検する。

1. 「提出前の自己チェックリスト」で点検する。読みやすさの項目を先に見る。文体を整えても、縦に長い文章の塊のままではレビュアーは読まない。
2. 文章を点検するスキル (AI が書いた文章の兆候の点検、文章校正など) が使える環境なら、本文をファイルに書き出し、そのスキルの手順で点検する。スキルに検出器やスクリプトがあれば実行する。
3. 初見の読み手に読ませる。書いた本人は、省いた主語や内輪の呼び方を文脈で補って読めてしまうので、自分の点検では見つからない。サブエージェントを使える環境では、差分も経緯も渡さず、PR のタイトルと本文だけを渡して、下の 4 点に当たる箇所を文ごとに挙げさせる。使えない環境では、書いた経緯を脇に置き、本文だけを 1 文ずつ読んで同じ 4 点を当てる。
   - 誰が、または何がその動作をするのかが分からない文
   - 説明なしに使われていて、意味が取れない言葉
   - 一度読んだだけでは意味が取れない文
   - 段落どうしで、同じ書き出しや同じ文の並びが続く箇所
4. 2 と 3 の指摘ごとに、直すか、直さない理由を決める。直したら、直した箇所だけをもう一度 2 と 3 にかける。かけ直しは 2 回までとし、それでも残った指摘には直さない理由を付ける。

同時に複数の PR を出すときは、3 で全部の本文を一緒に渡す。1 本ずつでは、PR どうしで骨組みが揃っていることに気づけない。

すべての指摘に、直した結果か直さない理由が付いたら、次へ進む。

### 6. PR 作成

- `gh pr create` で PR を作成する
- 自分を Assignees に設定する
- 変更範囲に他の人が実装した箇所への確認事項が含まれるなら、`git log -S` でその実装者を特定してレビュアーに追加する

タイトル規約：

- 30文字以内
- prefix（`refactor:` / `fix:` / `feat:` / `chore:` など）を付けない
- 日本語だけで書く

### 7. screen-review 連携（UI 変更がある場合）

UI に影響する PR では、修正前後のスクリーンショットと動作確認 GIF を本文に自動添付する。

判定条件：

- フロントエンドのコードや静的アセットに変更がある
- ユーザー目線で見た目や挙動が変わる

該当しない場合はスキップ。素材がまだ無ければ screen-review スキルを発動し、その規約に従って素材を揃えてから戻る。素材がある場合は `<screen-review スキルのディレクトリ>/scripts/publish-pr.sh /tmp/claude-shots/<TOPIC>` を実行する。

### 8. インラインコメントの投稿

手順2で作成したインラインコメント案が存在する場合、必ず `gh api` を実行してPRにコメントを投稿する。対象は1行ではなく、意味的なまとまり（関数定義、ロジックブロックなど）を範囲指定する。

    gh api repos/{owner}/{repo}/pulls/{pr_number}/comments \
      --method POST \
      -f body="コメント内容" \
      -f commit_id="$(git rev-parse HEAD)" \
      -f path="対象ファイルパス" \
      -F line=終了行番号 \
      -f side="RIGHT"

複数行の範囲を指定する場合は `-F start_line=開始行番号 -f start_side="RIGHT"` を追加する。

## 提出前の自己チェックリスト

PR作成前に以下を確認する。1つでも該当したら本文を見直す。上から順に見る。

- [ ] 概要が 3 文、見出しが 6 個、本文が 1,200 字を超えていないか。文字数は `wc -m` で測る
- [ ] 2 文を超える箇条書き、3 文を超える段落がないか。前者は段落に、後者は削るか図・表・折りたたみに
- [ ] 判断を仰ぐ点が、その変更の段落の直後に「確認したい点：」で置かれているか。Alert は関わる場所に置かれ、概要直後は PR 全体に関わる 1 つだけか
- [ ] 結論の太字は、持ち帰る結論がある段落に 1 か所までか (「確認したい点」のラベルは別に数える)。太字だけを拾い読みして結論が分かるか。文全体を太字にした箇所や、`**` の内側の端に句読点・コロン・括弧がある箇所はないか
- [ ] 変更内容の段落が、どれも同じ書き出し、同じ文数、同じ長さの文になっていないか
- [ ] 原因や処理の流れの説明が 2 段落を超えていないか。超えたなら図に置き換えられないか
- [ ] 2 つ以上の条件で値が異なる箇所を文章で書いていないか。表にできないか
- [ ] 「変更していないもの」の列挙、空節、絵文字見出し、「変更の種類」チェックボックスが残っていないか
- [ ] 実装場所の識別子や業界用語の名前を本文で語っていないか。日本語化した語は元が復元できるか
- [ ] 同じ情報 (特に認可・セキュリティ) を複数の節で反復していないか

英字の混在、時制、語尾、括弧書き、言い訳がましい表現は文体ルールの節、AS-IS/TO-BE の扱いは PR 構造の節に従う。

## 注意事項

- issue との紐付けがある場合は `Closes #123` を概要に含める
- 別リポや対になる PR を参照するときは `#NN` ショートハンドでなくフル URL を使う
- レビュアーの時間は有限。「読めばわかること」は書かない

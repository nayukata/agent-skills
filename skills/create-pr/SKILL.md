# PR を作成する

## 併用する文章規範

PRタイトル、PR本文、インラインコメントを書く前に、`../japanese-tech-writing/SKILL.md`を全文読む。
論証のつながり、読み手の負荷、冗長性、事実と推測の区別に適用する。

プロジェクトのPRテンプレート、GitHub記法、必須出力形式は、このskillの指定を優先する。
文章の温度感や語尾についても、このskillの文体ルールを優先する。

## 前提

コードレビューの本質は「バグ発見」ではなく「これは自分たちのプロダクトに組み込むべきか」というチームの判断行為である。
PR作成者の責務は、レビュアーがその判断を下せるだけの文脈を提供すること。
大量の情報で圧倒するのではなく、コードリーディングの助けとなる説明文を書く。

## 目的

- レビュアーの認知負荷を最小化する
- 実装や変更の意図を正しく伝える
- 不明点は推測で記述せず、ユーザーの意図を確認する

## 文体ルール

### 英字の使い方

地の文はカタカナ・ひらがな・漢字で書く。英字を書いてよいのは、製品・技術の正式名称、日本語に定着した略語、バッククォートで囲んだコード識別子のみ。

迷ったら以下の順で判断する。

1. その英単語はコードやAPIの識別子・概念名を指しているか？ YES ならバッククォートで囲む。
2. 普段のチャットや会話で自然に口から出るカタカナ語か？ YES ならカタカナ化。
3. どちらでもなければ日本語で書く。

英字の動詞（`unskip` / `propagate` / `resolve` 等）とカタカナで意味が通らない英単語（`wire format` / `composition` 等）は必ず日本語化する。

このルールは「識別子を残す線引き」を上書きしない。エンドポイントのパス、コマンド、環境変数名は、英字であってもバッククォート付きでそのまま書く。

### 時制

PR本文の動作記述は完了形で書く。「〜します」を裸で使わない。

| 何を書く | 時制 |
|---|---|
| 本PRに含まれる変更 | 完了形（〜しました） |
| 意図・目的 | 名詞化（〜が目的です） |
| 変更前の状態 | 過去形（〜されていました） |
| 過去の観測・報告 | 過去形（〜発見しました） |
| 変更後の体験 | 現在形（〜できます／〜されます） |
| 本当の未来 | 時系列マーカー付き（これから〜・別PRで〜・〜予定です） |

### 敬語と語尾

- 自然な敬語（〜です／ます／しました／お願いします／思います）
- 同じ語尾を連続させない
- 「〜してしまう」は望ましくない結末専用。望ましい変更を説明する文脈では「〜にする」と書く

### 事実と推測

差分から分かる事実に推測形を使わない。本当に推測のときだけ推測形にする。

### 言い訳がましい言い回しを避ける

「〜位置づけです」「〜見当たりませんでした」「〜する余地があります」「〜になりうります」といった間接表現は使わない。事実は完了形で断言、必要性がなければ書かない。

将来リスクの回避提案は前提が実在するか確認してから書く。前提が実在しないなら書かない。

### 業界用語の名前は本文に残さない

平文で説明できる技術用語は、平文で書き切る。用語名を括弧書きで添える必要はない。用語自体が話題（用語比較、用語選定の議論）の時だけ用語名を書く。

### 言い換えで抽象度を上げない

日本語化は、置き換え先が元の語と同じ範囲を指すときだけ行う。置き換えた結果、意味の範囲が広がる、または別分野の語として読めるなら、その言い換えは使わない。定着したカタカナ語で書くか、対象の具体物をバッククォート付きで書く。

判断は2点。置き換え先だけを読んで元が何だったか復元できるか。法務・契約・組織など別分野の話と誤読されないか。どちらかが落ちたら不可。

滑らせやすい置き換え：API 仕様を「契約」、エンドポイントを「窓口」「入り口」、ユーザー ID を「識別子」「目印」、リクエスト本文を「中身」、キューを「待ち行列」、コールバックを「呼び戻し」。

### 括弧書きの補足は最小限

括弧書きは視線を切って戻す動作を強いる。重要な情報なら普通に書き、要らないなら消す。

## PR構造

### 標準の3節

デフォルトは以下の3節のみで書く。

    ## 概要
    [この PR で何が変わるかを 1-3 文で。ユーザー/システム視点で]

    ## 変更内容
    [箇条書き。目的が複数なら見出しで分割]

    ## 動作確認
    [箇条書き。再現前提は必要な時のみ]

### 追加できる節（該当時のみ、空なら書かない）

| 節 | 書くのは... |
|---|---|
| `## 設計の意図` | 差分だけでは判断ポイントが読み取れない設計判断がある時 |
| `## トレードオフ` | 検討した代替案を捨てた理由を残したい時 |
| `## 影響範囲` | 変更が他コンポーネント/機能に波及する時 |
| `## レビューしてほしいポイント` | レビュアーに特に判断を仰ぎたい箇所がある時 |
| `## 関連リンク` | 対のPR・仕様書がある時 |

- 空節は削除する。「なし」「TBD」と書かない
- 関連PRは概要末尾に1行で書ける場合はインライン化

### AS-IS/TO-BE 節を独立に書かない

「変更前／変更後」を独立節に切り出さない。状況変化を書く時は、変更内容の各見出しの中で「これまでは〜／〜しました」の物語1本にまとめる。純リファクタでは省略。

### 絵文字テンプレは廃止

判で押した絵文字見出しと「変更の種類」チェックボックス群は情報の粒度差を潰す。テンプレに従わず、内容に応じて必要な節だけ残す。

## 変更内容の書き方

### ユーザー観点で振る舞いを書く

本文には振る舞い（何が起きるか）と設計判断（なぜそうしたか）だけ書く。実装の場所（ファイルパス・関数名・変数名・クラス名）は書かない。差分で見えるため。

主語はコンポーネント名やファイル名でなく、「ユーザーの体験」や「機能の仕様」にする。

### DB内部語彙で抽象化しない

「保存先」「テーブル」「レコード」「行」は差分の読者にも遠回り。ユーザーから見える現象で書く。

### 判断の観点を明示する

以下の観点は、変更が触れる範囲で PR本文で扱いを明示する。触れないとレビュアーには「作者はここを考えていない」と読まれる。

- 正常系だけでなく異常系（エラー・空データ・境界値・タイムアウト）の扱い
- 認証境界（認証・認可の対象範囲、誰が何を触れるか）
- 既存機能への影響（他のフローが壊れないか、壊れる場合の補償）

これらは変更内容・動作確認・レビューポイントのどこかで触れる。全てを常に書く必要はない。

### 識別子を残す線引き

以下のケースは識別子を書いてよい。

- 中心概念で本文中に繰り返し参照される（PRの主題そのもの）
- 削除対象の名指し
- 範囲の説明として不可欠
- 議論の対象そのもの（命名レビュー、除外リスト等）
- 場所の特定手段（エンドポイントURL、コマンド）
- 外部要因の根拠（使用ライブラリ名、API仕様名）
- デプロイ手順・利用者が設定する対象（実行コマンド、環境変数）

コマンド識別子（`make format` 等）はバッククォート付きで本文に残してよい。

### 概念（`識別子`）の初出補足形

初出で内部用語を出すときは **概念を普通の言葉で書いて太字**にし、**識別子は（`code`）で添える**。

### 反復禁止

同じ情報を概要／変更内容／動作確認／レビューポイントで書き重ねない。1度だけ、一番読ませたい場所に置く。

セキュリティ・認可話は特に反復されがち。書き終えたら「認可の話を何回書いたか」を数える。

### バグ修正／リファクタでも挙動変化は独立見出しで明示

- リファクタでもユーザー可視の変化があれば独立見出しで切り出す
- 「バグ修正」ラベルだけでは足りない場合、挙動変化節を切り出す
- 純リファクタは「挙動不変」を最初に明言し、AS-IS/TO-BE を書かない

### 「刷新」「修正」の区別

- 新規実装を「修正」「刷新」と書かない
- 既存の挙動を変えるのが「修正」
- 新しい機能を追加するのが「新規」
- 環境整備は「対応」

## 折りたたみ `<details>`

`<details>` は本流には不要だが深掘りしたい人には残しておきたい情報に使う。レビュアーに判断してほしい情報は折りたたまず本文に置く。

- 使う：長大なテストログ、失敗した代替案の詳細、テンプレの義務項目/チーム慣習で書きたい「変更ファイル一覧」等の機械的な列挙
- 使わない：レビューポイントで名指しした対象、動作確認の結論、設計判断の中核、レビュアーに判断してほしい設定値

## GitHub の視覚補助

### GitHub Alerts

重大な注意点・破壊的変更・移行手順の警告に使う。`> [!NOTE]` `> [!TIP]` `> [!IMPORTANT]` `> [!WARNING]` `> [!CAUTION]` の 5 種。

### Mermaid 図表

以下に該当する変更で強く推奨。

- 状態遷移の変更 → `stateDiagram-v2`
- コンポーネント・モジュール間の依存関係変更 → `graph LR` / `flowchart`
- API 呼び出し順序・複数システム連携 → `sequenceDiagram`
- DB スキーマ変更 → `erDiagram`

## 実行手順

### 1. 差分の把握

- `git log` と `git diff` で変更の全体像を把握する
- 変更ファイル数が多い場合は、意味的なまとまりでグループ化して理解する

### 2. インラインコメントの計画（必須出力）

PR本文を作成する前に、以下の条件に該当する箇所を探し、必ず「インラインコメント案」としてテキストに書き出す（出力する）。

- 差分だけでは意図が読み取りづらい複雑なロジック
- 一見不自然に見えるが理由がある実装（ワークアラウンド、制約回避など）
- レビュアーが「なぜこうしたのか」と疑問に思いそうな判断ポイント
- なるべく1、2行に収める
- その差分だけを読む人に伝わる自己完結した内容にする
- コード側に既にコメント（`# ...` / `// ...`）が付いている箇所には重ねない。二重コメントになる

該当箇所がない場合でも「インラインコメント対象：なし」と出力する。

出力フォーマット：

- 対象ファイル
- 対象コードの概要と行数の目安
- コメント内容

### 3. PR テンプレートの確認

    ls .github/pull_request_template.md .github/PULL_REQUEST_TEMPLATE.md .github/PULL_REQUEST_TEMPLATE/ pull_request_template.md 2>/dev/null

テンプレートが存在する場合、絵文字見出し・「変更の種類」チェックボックス・空節は本PRで採用しない（削除して提出）。チーム慣習で「変更ファイル一覧」等のテーブルを書きたい場合は `<details>` に畳んで本流の可読性を保つ。

テンプレートが存在しない場合、標準の3節（概要／変更内容／動作確認）を使う。

### 4. 動作確認項目の前提（再現条件）を明記する

動作確認・確認項目を書くときは、その確認を再現するための前提を必ず添える。

- 対のPR・別リポ・別ブランチを同時に動かす必要があるか
- 特定の環境変数・フィーチャーフラグ・seed データが必要か
- 起動が必要なサービス、または接続先
- マイグレーションやデプロイの順序指定

複数のリポ/PRが揃って初めて動く変更は、片方の PR しか見ないレビュアーが必ずいる前提で、関係する各 PR に前提を書く。

### 5. PR 作成

- `gh pr create` で PR を作成する
- 自分を Assignees に設定する

タイトル規約：

- 30文字以内
- prefix（`refactor:` / `fix:` / `feat:` / `chore:` など）を付けない
- 日本語だけで書く

### 6. screen-review 連携（UI 変更がある場合）

UI に影響する PR では、修正前後のスクリーンショットと動作確認 GIF を本文に自動添付する。

判定条件：

- フロントエンドのコードや静的アセットに変更がある
- ユーザー目線で見た目や挙動が変わる

該当しない場合はスキップ。素材がまだ無ければ screen-review スキルを発動し、その規約に従って素材を揃えてから戻る。素材がある場合は `<screen-review スキルのディレクトリ>/scripts/publish-pr.sh /tmp/claude-shots/<TOPIC>` を実行する。

### 7. インラインコメントの投稿

手順2で作成したインラインコメント案が存在する場合、必ず `gh api` を実行してPRにコメントを投稿する。対象は1行ではなく、意味的なまとまり（関数定義、ロジックブロックなど）を範囲指定する。

    gh api repos/{owner}/{repo}/pulls/{pr_number}/comments \
      --method POST \
      -f body="コメント内容" \
      -f commit_id="$(git rev-parse HEAD)" \
      -f path="対象ファイルパス" \
      -F line=終了行番号 \
      -f side="RIGHT"

複数行の範囲を指定する場合は `-F start_line=開始行番号 -f start_side="RIGHT"` を追加する。

## 提出前の自己チェックリスト

PR作成前に以下を確認する。1つでも該当したら本文を見直す。

- [ ] 地の文にバッククォート外の英字（製品名・略語以外）はないか
- [ ] 英字動詞・カタカナで意味が通らない英単語が残っていないか
- [ ] 実装場所の識別子を本文で語っていないか
- [ ] 「〜します」を裸で使っていないか
- [ ] AS-IS/TO-BE 節を独立に書いていないか
- [ ] 認可・セキュリティ話を複数箇所で反復していないか
- [ ] 括弧書き補足は必要か、平文化できないか
- [ ] 業界用語の名前を括弧書きで残していないか
- [ ] 日本語化した語を単独で読んで、元が何だったか復元できるか
- [ ] 言い訳がましい表現がないか
- [ ] 空節（内容が「なし」）は残っていないか
- [ ] 絵文字見出し・「変更の種類」チェックボックスは削除したか
- [ ] タイトルにprefixを付けていないか
- [ ] 変更が触れる範囲で、異常系・認証境界・既存機能への影響を明示したか
- [ ] コード側の既存コメントを繰り返すインラインコメントを付けていないか

## 注意事項

- issue との紐付けがある場合は `Closes #123` を概要に含める
- 別リポや対になる PR を参照するときは `#NN` ショートハンドでなくフル URL を使う
- レビュアーの時間は有限。「読めばわかること」は書かない

# UX 法則によるレビューと改善提案

## このスキルの位置づけ

既存 UI または設計案に対して発動する。**アプリ設計レベル**（画面構成、情報階層、ユーザーフロー、機能の取捨選択）の問題を 10 の UX 法則で根拠づけて指摘し、推奨改善案を 1 つずつ示す。コンポーネントの実装詳細（px、ms、プロパティ）は本スキルの範囲外で、実装時の別タスクに委ねる。

UI を扱うスキルなので、改善案は**視覚で比較できる形**で示す。デフォルトは既存サービス参照（「楽天トラベルのヘッダー検索のように」）、独自構造のときのみ構造図を追加する。

## このスキルが強制する 4 つのこと

- 主要ユーザータスクを 1 本特定し、そのタスクに効く法則を 3〜5 個に絞る
- 問題箇所を 3〜5 件特定し、各問題に**推奨改善案を 1 つ**示す（複数案の並列は禁止）
- 推奨改善案には既存サービス参照を default で添える（独自構造のときのみ構造図）
- user が「他の案も見せて」と明示的に要求した場合のみ、A 案 / B 案を追加で提示する

## いつ発動するか

発動条件

- 既存 UI のレビューを依頼された
- 新規 UI の設計方針を決める（「サンプル出して」「方針を提案して」等）
- 既存 UI の改修方針を決める
- 情報設計・画面遷移・機能構成の判断
- インタラクションパターンの選定
- UX 品質や使いやすさが論点になる場面

非発動条件

- バックエンドのみの変更
- タイポ修正、スタイル微調整で既存パターンを踏襲する場合
- ロジックのみで UI 表面を持たない変更
- コンポーネントの実装詳細（px / ms / プロパティ）の決定

## ワークフロー

応答の冒頭にチェックリストをコピーし、進捗を追いながら実行する。

```
UX-Aware Review Progress:
- [ ] Step 1. タスク特定 — 主要ユーザータスクを 1 本書き出す
- [ ] Step 2.0. ドメイン特定 — 対象サービスの業界カテゴリを確定する
- [ ] Step 2. 観察 — 既存 UI、関連フロー、業界標準を読む
- [ ] Step 3. 法則選択 — タスクに効く法則を 3〜5 個に絞る（内部）
- [ ] Step 4. 指摘抽出 — 問題箇所を 3〜5 件特定する
- [ ] Step 5. 改善提案 — 各指摘に推奨改善案を 1 つ示す
- [ ] Step 5.5. 慣習チェック — 推奨改善案が対象領域の慣習空間内にあるか
- [ ] Step 6. レビュー出力 — テンプレートで報告
```

### Step 1. タスク特定

主要ユーザータスクを 1 本、**「ユーザーは〜する」動詞文**で書き出す。複数候補がある場合は主タスクを 1 本選び、残りを副タスクに区別する。主タスクの摩擦を最小化することが第一目的。

**実装論・構造論の混入は禁止**。主タスクは「ユーザーが何をするか」だけを書く。

良い例

- 主タスク — ユーザーは必要な項目を入力し、内容を確認したうえで処理を確定する
- 副タスク — ユーザーは過去の履歴を参照する

悪い例（実装論・構造論が混入）

- ✗ 「Compound Pattern で Menu.Root を構成する」 — 実装方法であってタスクではない
- ✗ 「30 個のトグルをマトリクスで扱う」 — 構造選択であってタスクではない
- ✗ 「楽観的更新 + Undo Toast を採用する」 — 設計判断であってタスクではない

タスクは **ユーザーを主語、動詞を述語** とする能動態 1 文で終わらせる。

### Step 2.0. ドメイン特定（Step 2 の前に必ず実行）

代表サービスを選ぶ前に、対象サービスのドメイン（業界カテゴリ）を必ず特定する。**ドメインを誤認すると、的外れな参照（EC サイトのレビューに Linear を引く等）が出て、user の信頼を即座に失う**。

特定手段（リポジトリ内、上から順に試す）

- `README.md` `package.json` のサービス名・説明文・キーワード
- ブランド名、サービス名、独自ドメイン名
- 画面ファイル名、ルーティング（`/cart` `/checkout` `/booking` `/transfer` `/playlist` 等）
- ドメインを示すエンティティ名（`Product` `Reservation` `Account` `Patient` `Track` 等）
- 主要な依存ライブラリ（決済 SDK、地図 API、医療系ライブラリ等）

特定できなかった場合のみ `AskUserQuestion` で「対象サービスのドメインは何ですか」を user に確認する。**勝手に推測してドメインを決めない**。

ドメインが特定できたら、そのドメインの代表サービス 3〜5 個を選び、Step 2 の観察と Step 5 の参照に使う。**別ドメインの代表サービス（SaaS の例を EC レビューに引く等）を混入させない**。

ドメイン例と代表サービスの対応

- EC（家電、アパレル、書籍等） — Amazon、楽天市場、ヨドバシ.com、ZOZOTOWN 等
- SaaS（プロジェクト管理、コラボ） — Asana、Notion、Linear、Slack 等
- 銀行・送金 — 三菱 UFJ ダイレクト、住信 SBI、PayPay 銀行等
- 旅行予約 — 楽天トラベル、じゃらん、Booking.com、Airbnb 等
- 動画配信 — Netflix、YouTube、Amazon Prime Video 等
- 地図・配車 — Google Maps、Uber、GO、タクシーアプリ等

リストにないドメインの場合は、user に代表サービスを確認するか、対象ドメインの代表サービス 3〜5 個を自分で挙げて出力に明示する。

### Step 2. 観察

判断の前に、関連する現物から事実を集める。観察結果は Step 4 の指摘根拠として引用する。

集めるべき事実

- 既存画面の役割と画面遷移（どの画面からどの画面へ）
- プロダクト内の情報階層（トップレベル、セカンダリ、詳細）
- 同カテゴリの業界標準アプリがどんな画面構成を採っているか
- 主要ユーザーフローの所要ステップ数と分岐点
- 既存パターンと外す場合のコスト

取得手段

- コード — `Read` `Grep` `Glob` で既存画面ファイルやルーティングを読む
- 稼働 UI — ブラウザ操作ツールで主要フローを辿る
- デザインツール — Figma 連携ツール等で画面構成を取得

動的コンテンツの境界ケース観察（必須）

UX 判断は最適ケースでなく境界ケースで評価される。次の 5 パターンを必ず想定する。

- **最長テキスト** — 項目名・説明文が最長のときの扱い（折り返し、ellipsis、表示領域）
- **最短テキスト** — 1 文字や空文字のときの見た目（最小表示、空欄扱い）
- **空データ** — リストが 0 件、情報未取得の扱い（empty state の設計）
- **最大件数** — リスト上限時の扱い（一覧表示か、ページング / 仮想化か）
- **最小件数** — リストが 1 件のときの見た目（グリッドが崩れないか）

これらを想定していない指摘・改善案は本番で必ず崩れる。

観察できない場合の代替手順

実コード・実画面・実 Figma にアクセスできない場合でも、業界標準からの参照で代替できる。次の手順を必ず踏む。

1. 対象領域の代表サービスを 3〜5 個選ぶ
2. それらに共通する画面構成・フロー・情報階層を典型として抽出する
3. 出力の「観察」セクションに「観察していない。代わりに X / Y / Z を参照した」と明示する

勝手に観察したフリをしない。「観察していない」を明示することで、user が実観察の必要性を判断できる。

### Step 3. 法則選択

10 すべてを機械的に並べない。タスクと観察に照らして **3〜5 個に絞る。最大 5 個が上限であり、6 個以上は禁止**。

6 個以上に膨張した場合は、タスクとの結びつきが弱い法則から削る。1 つの指摘に複数の法則が効く場合は、最も支配的な法則 1 つだけを内部メモに残す。

各法則が効く場面

- **ポステルの法則** — 入力の受け入れ範囲と正規化、情報の出し方
- **ミラーの法則** — 情報チャンクの単位、一度に提示する項目数
- **ヒックの法則** — 選択肢の数、機能の露出 / 格納、分岐の設計
- **実行の隔たり / 評価の隔たり** — 操作意図が伝わる導線と、結果のフィードバック設計
- **テスラーの法則** — デフォルト、隠す / 見せるの境界、上級者向け機能の配置
- **ヤコブの法則** — 業界慣習との一致度、どの画面パターンを採用するか
- **フィッツの法則** — 主要操作の到達性、危険操作の隔離、配置方針
- **ピーク・エンドの法則** — 重要なジャーニーの開始と終端の扱い
- **ドハティのしきい値** — 体感応答、ローディング / 遷移の知覚速度
- **ゲシュタルトの法則** — 情報の視覚グルーピング、階層、余白の意味

選ぶときは、各法則について次の 1 文を自問する。

> 「この法則は、Step 1 で書いた主タスクのどこに効くか」

答えられない法則は選ばない。法則の名前で選ぶのではなく、主タスクとの結びつきで選ぶ。

**選んだ法則は agent の内部思考でのみ使う**。user 向け出力（Step 6）には法則名を書かず、平易な日本語に翻訳する。法則を知らない user には「ヒック」「ヤコブ」と書かれても意味不明で、内輪の符号になる。

### Step 4. 指摘抽出

主タスクと観察に照らして、既存 UI または設計案の問題箇所を **3〜5 件**特定する。**6 件以上は禁止**。

各指摘について次を内部で整理する。

- 何が問題か（1 文）
- 観察した事実（既存 UI のここがこうなっている、または設計案のここがこうなる）
- 主タスクへの影響（1 文）

問題対象の例

- 画面構成の問題（情報過多、優先順位不明）
- 情報階層の問題（重要情報が埋もれる、副次情報が前面）
- ユーザーフローの問題（無駄なステップ、分岐の混乱）
- 配置の問題（主要操作が遠い、危険操作の隔離不足）
- インタラクションの問題（慣習外、フィードバック不足）

6 件以上に膨張した場合は、主タスクとの結びつきが弱いものから削る。

### Step 5. 改善提案

各指摘に対して **推奨改善案を 1 つだけ**示す。**A 案 / B 案 / C 案 の並列提示は禁止**。

各改善案について次を整理する。

- 推奨案（1 行、既存サービス参照を default）
- なぜこの改善が効くか（1 文、平易な日本語）

改善案を検討する順序（足す前に乗せる）

新しい UI 要素を足す前に、既存のものに乗せられないか問う。次の順序で代替案を検討し、上のほうで成立する案を採用する。

1. **既存動線・既存要素への組み込み** — ユーザーが既に通る画面・状態（一覧の行、ホバー領域、確定ダイアログ、ヘッダー、トースト等）に必要な情報や操作を埋め込めないか
2. **既存 UI の組み換え** — 並び順、表示密度、視覚的階層、グルーピングの調整で解決できないか
3. **新 UI 要素の追加** — Drawer / Modal / 新ページ / 新ボタンなど

下の階層ほど学習コストが膨張する。「専用ページを作れば」「新しいコンポーネントを足せば」と感じた瞬間に、上の階層で再構成できないかを 1 度問い直す。

同じ対象を扱う UI は情報粒度を揃える

同じドメインオブジェクトに対してユーザーが同じ意思決定をする複数の UI コンテキストでは、表示する情報粒度を揃える。

該当する場面の例

- 一覧 / 詳細 / プレビュー / 確認ダイアログ
- ホバーカード / サイドパネル / フルページ
- 削除前 / アーカイブ前 / エクスポート前など、対象が同じで操作だけ異なる確認画面群

操作の重要度や性質の違いは、情報量ではなく**色・ラベル・確定ボタン・警告文**で表現する。情報量で差別化すると「軽い場面だから注意しなくていい」という誤った注意度シグナルを送り、ユーザーが UI ごとに別のパターンを学習する負担も生じる。

視覚化の方法

UI 構成を伝える手段は 2 つあり、状況に応じて使い分ける。

**1. 既存サービス参照（デフォルト）**

「楽天トラベルのヘッダー検索のように」「Apple のサイトのように」など、user が知っている既存サービスの該当パターンを参照する。慣習空間内に閉じる skill 設計と相性が良く、軽量で確実に伝わる。各改善案の頭に 1 行で書く。

**2. 構造図（必要な時のみ）**

参照だけで伝わらない独自構造、または配置の差が UX 結果に直結する場面では構造図を追加する。罫線テーブル（`┌─┐│└┘├┤`）は monospace でも全角/半角混在で崩れるので禁止。**セクションラベル + 縦インデントリスト** で表現する。

構造図が必要な判定基準

- 業界に同等の参照例がない独自配置
- 階層関係が複雑（3 階層以上）
- 配置の差が UX 結果に直結する場面

これに当てはまらない場合は、参照だけで十分。

代替案の扱い

user が「他の案も見せて」「別の選択肢は？」「複数案を比較したい」と明示的に要求した場合のみ、該当する指摘に A 案 / B 案 / C 案 を追加で提示する。要求がない限り、推奨 1 案で完結させる。

### Step 5.5. 慣習チェック（最終ゲート）

提案する全改善案（画面構成、フロー、配置、インタラクション）を、対象領域の大衆ユーザーが既に見たことがある慣習空間内のものに限定する。

実行手順

1. Step 5 で出した各推奨改善案について、対象領域での代表的な実装例を 2〜3 個挙げられるか自問する
2. 挙げられない場合、それは慣習空間外のパターンの可能性が高い
3. 慣習空間内に同じ目的を達成する既知の代替パターンがあれば、そちらに差し替える
4. どうしても慣習空間外を提案したい場合は、`AskUserQuestion` で「対象領域では未知のパターンですが提案してよいか」と事前確認する

判定基準

- ◯ 提案パターンが、対象領域の代表サービス 2〜3 個で採用されている — 慣習内
- ◯ 提案パターンが、対象領域の既存慣習の軽微な変種として成立している — 慣習内（亜種として許容）
- ✗ 提案パターンが、別領域（例 — 車載 UI、エンタメアプリ、ゲーム）でのみ見られ、対象領域では採用例がない — 慣習外
- ✗ 提案パターンが、対象領域のどの代表サービスにも存在しない独自発明 — 慣習外

「フィッツ逆適用が必要」「より安全な代替がある」など法則的に正しい判断であっても、選ぶ代替は慣習空間内から選ぶ。

### Step 6. レビュー出力

下記テンプレートで報告する。順序は固定。**横長テーブルは使わない**。各項目を見出し + 縦リストで展開し、ビューポートが狭くても崩れない形にする。

```
## UX レビュー

### 主タスク
[ユーザーが達成したいことを 1 文]

### 観察
[既存 UI / 関連フロー / 業界標準の参照点を 1〜2 文で]

### 指摘と推奨改善（3〜5 件）

#### 1. [問題対象]
- **現状**: [既存 UI の事実 1 文]
- **問題**: [主タスクへの影響 1 文]
- **推奨改善**: [既存サービス参照、または 1 行説明]

（独自構造の場合のみ、構造図を追加）
\`\`\`
[縦インデントリスト構造図]
\`\`\`

#### 2. [問題対象]
（同じ構造）

（必要に応じて 3、4、5 を追加。6 件以上は禁止）

### スコープ外
[今回扱わないものを 1〜3 点。コンポーネントの実装詳細はここに含める]
```

ルール

- 1 指摘あたり「現状 + 問題 + 推奨改善」の 3 行で完結。長文化禁止
- 推奨は必ず 1 案。複数案の並列は user が明示要求した場合のみ
- 画面構成セクションは出さない（指摘で必要部分は触れている）
- 衝突セクションは出さない（推奨を 1 つに絞ったので衝突は出てこない）
- 出力後に「どれで進めますか？」と user に選択を投げない（推奨が 1 案なので選ばせる対象がない）

## 落とし穴

- **観察スキップ** — 既存 UI を見ずに指摘を出すと一般論になる。Step 2 を必ず通す
- **変動コンテンツの無視** — 最長文字列・空データ・最大件数・最小件数の境界ケースを想定しない指摘は本番で崩れる
- **主タスクの実装論化** — 主タスクに「Compound Pattern」「マトリクス構造」「楽観的更新」など実装方法が混ざると、指摘の軸がブレる。主タスクは「ユーザーが何をするか」を動詞文 1 文で書き切る
- **全適用症候群** — 10 法則すべてに触れる出力は、どれも刺さっていないサイン
- **指摘数の膨張** — 指摘を 6 件以上に並べるとどれも刺さらない。3〜5 件を上限として、削れない場合はスコープ外に移す
- **慣習の機械踏襲** — ヤコブを盾にデファクトをそのまま採用しない。タスク特性によっては逆適用が正解（不可逆操作など）
- **慣習空間外への飛躍** — 「慣習を破る」と「未知パターンに飛ぶ」は別物。代替を選ぶときは必ず対象領域内の既知パターンから選ぶ
- **ドメイン外参照の混入** — EC サイトのレビューに Linear や Notion の例を引く、銀行アプリのレビューに Slack の例を引くなど、対象ドメインと無関係な代表サービスを参照に使うと、user は「なぜこのサービスを引いた？」と即座に違和感を抱く。Step 2.0 で確定したドメインの代表サービスからしか参照を選ばない。ドメインを誤認したまま進めるくらいなら、`AskUserQuestion` で確認する
- **ピーク・エンドの軽視** — 失敗画面を「エラーメッセージ表示」で済ませない。失敗体験の終端は次回利用率に直結
- **指摘の散文化** — 「ユーザビリティを向上させる」のような抽象表現を禁止。問題対象と現状と推奨を具体で語る
- **コンポーネント粒度への降下** — 指摘や改善案が `ProductCard 48px` `200ms debounce` などのコンポーネント名・px・ms に降りたら、それは技術詳細で本スキル範囲外。実装時の別タスクに委ねる
- **視覚イメージなしの改善提案** — 改善案を文字だけで並べると user が比較できない。各改善案には既存サービス参照（「楽天トラベルのような」）または構造図のいずれかを必ず添える
- **罫線テーブルの崩れ** — 日本語と英数字を罫線（`┌─┐│└┘├┤`）で囲んだテーブルは、monospace フォントでも全角/半角の文字幅差でアラインが崩れる。罫線テーブル形式は禁止、セクションラベル + 縦インデントリストで表現する
- **不要な構造図** — 既存サービス参照だけで伝わる場面で構造図を出すと冗長。判定基準（独自配置、3 階層以上、配置差が UX 結果に直結）に当てはまらないなら参照のみで止める
- **法則名の出力混入** — UX 法則名（ヒック、ヤコブ、ピーク・エンド等）を user 向け出力に書かない。法則を知らない user には意味不明で、内輪の符号にしか映らない。法則は agent の内部思考用、出力は「選択肢が多いときの決断疲労を避ける」「業界慣習に合わせる」等の平易な日本語で表現する
- **複数案の自動提示** — user が要求していないのに A 案 / B 案 / C 案 を並列で出すと「結局どれ？」と困惑させる。推奨 1 案を default にし、複数案は user が明示要求した場合のみ
- **指摘なしの提案** — 現状の問題を示さずに改善案だけ出すと、user が改善の必要性を判断できない。必ず「現状 → 問題 → 推奨改善」のセットで提示
- **「どれで進めますか？」の禁止** — 推奨 1 案で完結する形なので、user に選択を投げ返さない。レビューは agent が結論を出すツールであって、user に決断を強いるツールではない
- **足し算思考の罠** — 「新しいページを作れば解決」「新コンポーネントを足せば解決」と感じた瞬間が、既存の動線・要素で再構成する選択肢を捨てるサイン。Step 5 のコスト階層で再検討する
- **コンテキストごとの情報量差別化** — 同じ対象を扱う UI で「ここでは簡略表示」「ここでは詳細表示」と差をつけると、一貫性が崩れて学習コストが増える。差別化は色・ラベル・配置で
